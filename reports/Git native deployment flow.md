# Deploy commits, not snapshots, from the user's repo

The right flow for Flowpad is the one Vercel, Netlify, Cloudflare and Render already use: **the user's git repo is the only source; a deploy builds one commit SHA; the platform keeps the built artifact, not a second git history.** When the project has no remote, Flowpad should do what Heroku and Hugging Face Spaces do: create a real remote and add it as the project's `origin`, so the user pushes their own history to it and every deploy is still a commit. Today Flowpad does the opposite. It copies the working tree, uncommitted files included, into a hidden mirror and pushes a synthetic "Publish FlowPad project" commit into a hub repo that shares no history with the user's repo. That repo then lives on a disk that every hub release wipes, while the database rows that point at it survive. The result is a deploy that cannot be traced to a user commit, cannot be rolled back, and fails with a misleading "try again shortly" after each hub release. The fix has three parts: identify every deploy by (commit SHA, artifact digest, config version); let sandboxes fetch that SHA with a short-lived token scoped to one repo; and store managed repos durably or not at all.

## The problem, as proven in this session

When a user publishes or deploys a project or agent, Flowpad copies the project's working tree, including uncommitted files, into a hidden local mirror clone at `~/.flow/instances/<inst>/hub_git/mirrors/<repo>`. It then pushes a synthetic "Publish FlowPad project" commit into a repo hosted by the hub. This happens even when the project already has a GitHub origin. In one proven case, a project linked to `langware-labs/gtm-studio` got hub repo `e3ffb75e`, and the published commit `fd7c5aa` is not in the user's git history. The user's repo is never connected to the hub repo. Deploy sandboxes (e2b and gcp) and recipients clone that snapshot repo.

The hub stores these repos with provider `local` under `/tmp/flowpad_temp/flowpad_git_storage/hosted` on the VM boot disk. Every hub release replaces the VM, so the repos are wiped. The rows that point at them (`git_repo`, the project's `git_origin`, the agent's `head_commit`) persist. The next deploy fails with **410 Gone**, which the UI shows as "try again shortly". Toggling storage on and off reproduced this. The user's stated principle is git native: their repo is the single source of truth, and the hub allocates a managed repo only when the user has none, as the project's `origin`, with the same history.

## Nine platforms split into three models, and two of them fit

Every platform surveyed falls into one of three models. **Repo is truth, platform keeps artifacts** (Vercel, Netlify, Cloudflare, Render, Railway): the platform clones a commit from the user's GitHub, builds it, and keeps an immutable artifact. **Platform hosts the remote** (Heroku, HF Spaces): the user adds the platform as a git remote and pushes their own history. **Upload a snapshot** (Fly CLI, Railway CLI, Replit): the working directory is sent with no commit attached. Flowpad today is a fourth, worse variant: a hosted remote with a synthetic history, which nobody else does.

Two lessons stand out. First, the snapshot-upload platforms (Fly, Railway CLI, Replit) are exactly the ones that lose commit identity, and Vercel staff say CLI deploys "are not treated as git deploys" and carry git metadata only for display ([Vercel community](https://community.vercel.com/t/cli-doesnt-send-gitsource-during-deployment-the-git-branch-url-is-not-generated/870)). Second, Heroku shows that a platform-hosted remote with ephemeral storage is acceptable only when it is *not* the source of truth: Heroku says its repo is not a backup and tells users to keep GitHub as the real home ([Heroku Git](https://devcenter.heroku.com/articles/git)). Flowpad's hub repo plays the opposite role. For no-remote users it is the only remote, so it must be as durable as HF's.

## The recommended flow, step by step

These steps combine the GitOps rule that one versioned source is pulled by agents ([OpenGitOps](https://opengitops.dev/)) with 12-factor's rule that a release is build plus config, with a unique, immutable ID ([12factor](https://12factor.net/build-release-run)).

1. **Resolve the source.** Read the project's `origin`. If it exists (GitHub or other), that is the source. Never create a hub repo for it.
2. **No remote: allocate one, as `origin`.** The hub creates a managed repo (preferably a `github_app` repo in a Flowpad org, or durable hub storage) and Flowpad runs `git remote add origin <url>` and pushes the user's existing history. From then on it is an ordinary remote, the same model as Heroku and HF.
3. **Handle a dirty tree before deploy.** Show the uncommitted files and offer one action: "Commit and deploy". It makes a normal commit on the current branch (or a `flowpad/deploy-<n>` branch if the user prefers) and pushes it. The default is never to upload uncommitted files silently. If an escape hatch is kept, record `dirty=true` plus a content digest, the way Vercel's `gitMetadata.dirty` and Wrangler's `--commit-dirty` do, and never label that deploy "commit X".
4. **Push, then deploy a SHA.** The deploy request names a repo and a full commit SHA, never a branch or a working directory. Confirm that the SHA exists on the remote before accepting the request.
5. **Record the deploy identity** as an immutable row: (repo, commit SHA, artifact digest, config version, target). Secrets and config changes create a new row, as Heroku's config changes create a new release ([Heroku Releases](https://devcenter.heroku.com/articles/releases)).
6. **Sandbox fetches with a short-lived scoped token.** The hub mints a token per job for that one repo with contents:read (write only if the agent must push results). GitHub App installation tokens expire after 1 hour and can be narrowed to specific repos and permissions ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). The e2b/gcp sandbox clones at that SHA, passing the token per call ([E2B git](https://docs.e2b.dev/sandbox/git-integration)), and never writes it into `.git/config`.
7. **Build once, keep the artifact.** Store the built output (or a pinned image digest) with retention that always protects the live deploy and the last N, as Vercel and Netlify do ([Vercel retention](https://vercel.com/docs/deployment-retention), [Netlify](https://docs.netlify.com/site-deploys/manage-deploys/)).
8. **Write results back to git.** Agents that change code push a branch or open a PR on the user's remote, the pattern used by Cursor and Codex cloud agents ([morphllm](https://www.morphllm.com/cursor-background-agents)). Optionally post a commit status with the deploy URL.
9. **Roll back by pointing at an old row.** A rollback creates a new deploy row that reuses an earlier artifact and config, with no rebuild, as Heroku, Render, Vercel and Netlify do. If the artifact has expired, rebuild from its SHA, which still exists in the user's repo.
10. **Recipients clone the same remote at the same SHA.** Sharing grants access to the user's repo (or the managed origin). There is no separate shared copy.

## Invariants that make the flow safe

Every deploy row names a commit that exists in the user's own history; a SHA reachable only in a Flowpad-private repo is a bug. Flowpad never keeps a second history of a project that has a remote, because a shadow copy breaks GitOps' "complete version history" in one place ([OpenGitOps](https://opengitops.dev/)). A deploy row is append-only. A managed repo's storage and its database row live and die together: GitLab bans snapshot backups of Gitaly Cluster precisely because the metadata DB and the disk drift apart ([GitLab Gitaly](https://docs.gitlab.com/17.7/ee/administration/gitaly)), and GitHub's Spokes refuses writes it cannot durably replicate rather than accept them ([GitHub DGit](https://github.blog/engineering/architecture-optimization/introducing-dgit/)). So managed repos never sit on `/tmp` or a boot disk. They go to a persistent volume with `git bundle` backups to object storage, or, more simply, to GitHub through `github_app`. Errors are typed: a missing repo is `repo_missing` (permanent, needs action), an expired token or uninstalled app is an auth error, and only network or 5xx errors are "try again". No sandbox holds a credential that outlives its job.

## Mapping to Flowpad pieces

**Desktop app / local backend** owns steps 1–4. It reads `origin`, shows the dirty-tree prompt, commits and pushes with the user's own git credentials, and sends `(repo, sha)` to the hub. The hidden `hub_git/mirrors` clone and the synthetic "Publish FlowPad project" commit go away. **Hub (app.flowpad.ai)** owns step 2 (allocating a managed origin only when there is none), step 5 (deploy rows), step 6 (minting scoped tokens via the `github_app` provider), and rollback. The hub's `git_repo` row becomes "a remote we manage" for no-remote projects and "a pointer to the user's remote" otherwise. Provider `local` is either moved to persistent, backed-up storage or retired in favour of `github_app`. **e2b and gcp_vm sandboxes** clone `repo@sha` with the per-job token and push results as a branch. **Agents** store `head_commit` as a SHA in the user's repo, plus the deploy row ID, not a SHA in a hub snapshot.

## Migrating from the current state

Run the migration in four moves. First, stop the bleeding: make the hub check that a repo exists on read and return a typed `repo_missing` error. The UI should then say "this project's deploy copy was lost; redeploy from your repo" instead of "try again shortly". Second, switch new deploys to the flow above behind the desktop app's deploy action. Projects with a GitHub origin deploy from it right away. Third, re-point existing rows: for every project with a `git_origin` on GitHub, set the deploy source to that origin and drop the hub snapshot repo. For agents, re-resolve `head_commit` to the user's latest pushed commit at the next deploy and treat snapshot SHAs such as `fd7c5aa` as legacy (they cannot be mapped to user history). Fourth, handle the lost repos. Rows whose `local` storage was wiped are not recoverable from the hub. The source still exists on each user's machine, so on next open the desktop app detects the orphaned row and offers either "Use my GitHub remote" or "Create a managed origin and push my history". Rows for projects nobody opens can be marked orphaned and cleaned up later. Any snapshot repos that survive should be kept read-only until their projects re-point, then deleted. They hold no history worth merging.

Some things remain unknown. The research did not establish per-plan artifact retention for Render, Railway or Cloudflare Pages, or exactly how the Vercel CLI computes `dirty`. Fly and Modal fetch mechanics were also not checked. None of these gaps changes the recommendation.

## Conclusion

The fault is not that Flowpad hosts git. It is that Flowpad treats a private copy as the source and then stores it like a cache. Heroku can get away with ephemeral storage because its repo is disposable by contract. HF Spaces can be the only remote because its storage is durable. Flowpad currently claims HF's role with Heroku's storage. Choosing durability (or delegating to GitHub) and making the SHA the deploy key removes the 410 failure, the untraceable deploys, and the rollback gap in one design decision.

The less obvious payoff is for agents. Once a deploy is `repo@sha` with a scoped token, a deployed agent's output can flow back as a branch on the user's repo. That turns deployment from a one-way publish into a loop the user can review in their normal git tools.
