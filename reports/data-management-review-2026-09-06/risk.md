**Risk analysis — proposed data-management fixes and consolidation**

Assessed 2026-09-06 against the review evidence and selected source paths at HEAD `abb4a1274d50b4bc9435cfb6845616cfe594ff8c`. This evaluates the proposed changes; it does not establish that any fix has been implemented or validated. Risk ratings are qualitative judgments based on persistence boundaries, affected callers, concurrency and reversibility. There is no production failure-rate dataset from which to assign probabilities.

**Assessment**

The full package has **high implementation risk as one combined change**, principally because it alters filesystem identity, two-way persistence, transaction publication, discovery completeness and stored formats together. Splitting it into narrowly verified changes makes the search/SDK reductions relatively tractable while exposing the migrations and persistence changes to stronger checks.

The current system also has material risk: the review reproduced acknowledged changes disappearing on reindex, nullable clears reversing, live shadows being removed, identity races and false absence in search. Correctness fixes deserve priority even where they add code. Treat the approximately 500-SLOC reduction as a planning estimate; persistence, compatibility and recovery invariants determine whether a change is ready.

**Coupled risks that need explicit design**

**Discovery completeness and identity ownership.** The current owner inventory selects a winner using creation time and ID, rather than encounter order. A streaming walker must retain that rule even when file enumeration becomes incremental. A parser error, inaccessible root, limit or cancellation cannot prove a source was deleted. Compare inventories through read-only planning or isolated copies: scan preview can currently mint/write carriers, so simply executing both implementations on the same live tree is not a passive comparison. Relevant seams: [PathOwnerIndex](/Users/shlom/Documents/dev/flowpad-oss/flow_sdk/fs_store/path_owners.py:90) and [orphan candidate calculation](/Users/shlom/Documents/dev/flowpad-oss/flow_sdk/fs_store/indexer/index_function.py:1279).

**Filesystem writes and DB commit.** A SQLite transaction cannot roll back a source file replacement. The implementation must specify what remains authoritative after a file write succeeds but projection commit fails, and how that partial completion becomes visible and repairable. Preserve disk→DB writeback suppression, distinguish explicit clears from omission, and define one lock order across identity, record and DB ownership. Reuse of the existing serializer alone does not prove every route writes existing assets correctly, because `owns_main_ref` and explicit-edit behavior differ by type. Relevant seams: [Entity.save](/Users/shlom/Documents/dev/flowpad-oss/flow_sdk/core/entity/entity_model.py:2470), [shadow merge](/Users/shlom/Documents/dev/flowpad-oss/flow_sdk/fs_store/fs_record.py:540), and [serializer write policy](/Users/shlom/Documents/dev/flowpad-oss/flow_sdk/fs_store/serializer/disk.py:203).

**Events and session lifetime.** Moving publication after commit changes timing for real consumers, including workflow rearming. Queue immutable payloads; resolve publication at the outer transaction's actual commit boundary, including index batches. Awaiting a consumer that needs a resource still held by its publisher can stall the operation. After-commit in-memory dispatch also leaves a crash window between commit and publication. Decide whether recoverable notification loss is acceptable; a durable outbox is additional scope only if delivery across crashes is a requirement. Relevant evidence: [RE4–RE5](/Users/shlom/Documents/dev/flowpad-oss/reports/data-management-review-2026-09-06/records-entities.md).

**Completion tokens and migration.** Mark a projection complete for the source snapshot actually parsed and the producer/index generation actually committed. If source content changes during parsing, the newer content must remain eligible for refresh. FTS backfill must not use the currently unsafe global clear/rebuild path as its repair mechanism. Include searchable DB-only types in migration design; a filesystem walk alone cannot reconstruct their projections. Old/new sentinel and sidecar readers need an explicit compatibility policy before new writers are enabled. Relevant evidence: [index-generation and sidecar findings](/Users/shlom/Documents/dev/flowpad-oss/reports/data-management-review-2026-09-06/index-search.md).

**Rollout sequence and acceptance criteria**

1. **Protect existing data with narrow fixes.** Repair destructive cleanup evidence and reset scope/guard ownership. Fix acknowledged-write loss, explicit clears and stale refresh in small type-aware changes. Start with the review's failing fixtures; require unaffected projects, IDs, source bytes and authoritative DB-only rows to remain intact. These changes may add SLOC.
2. **Establish transaction and identity ownership.** Implement carrier locking, session ownership and after-commit publication with concurrency/failure-injection coverage. Exercise create, edit, discover, reindex and delete against the same temporary corpus. Accept the change only when callbacks do not observe uncommitted state or retain sessions past their owner's lifetime.
3. **Consolidate query and SDK paths.** Keep both route response adapters and the existing public hook contracts. Verify independent expected result sets, counts and membership; use the old output only where its behavior is known to be correct. Measure query plans and request/subscription counts before deleting duplicated orchestration.
4. **Consolidate discovery.** Introduce the shared filtered candidate stream and owner projection. Compare candidate sets and selected identities on representative fixtures; test errors, cancellation and partial roots. Verify cleanup separately from enumeration performance. Require bounded parsing/memory and continued HTTP/event-loop responsiveness under unchanged timeout caps.
5. **Migrate persisted formats and reduce stored content.** Establish compatibility readers and recoverable snapshots before enabling new writes. Test interrupted migration and supported downgrade behavior. Remove old adapters/fields only after their consumers and recovery paths have been checked; then recount net SLOC.

Useful rollout signals are unexpected UUID changes, source/shadow mismatches after roundtrip, removal of live/unreachable candidates, row/FTS generation disagreement, scope-filter result mismatches, retained callbacks, writer-lock contention and interrupted-index recovery failures. Compare these against the same fixtures and workload baseline. Any such correctness failure pauses expansion to additional types or instances; a smaller line count does not compensate for it.

**Rollback and recovery**

Pure request/subscription refactors usually need a code revert and cache refresh. Source-writing or format-changing work needs a coordinated recoverable snapshot of authoritative DB rows, shadows and affected assets, with writers controlled while capturing/restoring consistent state. A raw copy of one live SQLite database file is not itself evidence of a complete snapshot; use the project's validated backup path or verify a consistent SQLite backup together with filesystem state. Restore procedures must account for legitimate edits made after the snapshot.

Do not treat all SQLite data as disposable. The reviewed `db_only` branch intentionally omits filesystem shadows for operational/domain rows. Test recovery by preserving those rows and rebuilding only declared projections. Carrier identity changes and already-fired external workflow effects require reconciliation; neither is repaired merely by reinstalling an older binary. No backup, migration or deployment is being performed as part of this analysis.

**Estimate confidence and remaining uncertainty**

The 2,492-SLOC candidate baseline is measured. The 500–822 consolidation reduction and additional 100–200-SLOC safeguards allowance are estimates. Compatibility adapters, migration support or stronger event-delivery guarantees may exceed that allowance, bringing the full-package reduction below the earlier 300–720 range. Individual correctness batches will reasonably increase production code. Tests and documentation add further lines outside that estimate.

The review's reproductions establish current defects, not fix readiness. Unresolved scope includes the complete external SDK/CLI consumer inventory, older installed readers, platform-specific filesystem behavior, realistic multi-process write pressure, and deployed migration/recovery behavior. The most reliable initial commitment is staged correctness and measured consolidation; retain the aggregate SLOC target as a forecast until those boundaries are validated.
