# Criterion: structure

> Ground rules (inline by design): never delete knowledge; integrate, don't
> append; max 5 findings/corrections per pass; converged is a valid verdict.

The constraint on a skill is never too much knowledge existing — it is too
much loaded at once. Capacity is free; attention is scarce; loading is the
discipline. Judge structure by what reaches context, not by folder size.

1. **The entry file is an index, not a manual.** Once a skill outgrows one
   small file, SKILL.md becomes a routing table: rows of "when you need X,
   load Y". It points; it does not teach. A category file may itself be an
   index routing to sub-categories — depth is fine, the index staying thin is
   the invariant (the pod's budget: an index stays under ~300 lines no matter
   how big the tree grows).
2. **Each rule lives at the deepest level where it still gets seen.** A rule
   placed at the top because it "feels important" costs every session;
   importance and universality are not the same thing. Put it next to the step
   that needs it, so it loads exactly when relevant and never otherwise.
3. **Cross-cutting ground rules are inlined redundantly**, at the top of every
   file they govern — not centralized in one file others must remember to
   load. Inlined rules are always reachable; pointed-at central files get
   orphaned. The redundancy is structural integrity, not sloppiness.
4. **Unused content is never a delete candidate.** A file nothing loads means
   one of three things: a routing bug (no row surfaces it), a structure
   problem (sliced so it never matches a real task), or content rot (rewrite
   in place). Every fix preserves the knowledge.
5. **Repeated mechanical work belongs in `scripts/`**, referenced from the
   step that needs it — not re-derived in prose each run.
6. **Routing integrity is auditable**: every row in every index points at a
   file that exists, and every non-index file is reachable from some row.
   Orphans are findings.
